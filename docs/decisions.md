- Окружение сборки переведено на KenshiLib v0.5.0: vcxproj берёт заголовки из `third_party/community/kl050/Include` (тег v0.5.0; в релизном zip каталога Include нет), `KenshiLib.lib` из `third_party/KenshiLib_v0.5.0`, `OgreMain_x64.lib` из `KenshiLib_Examples_deps`, Boost 1.60 (только заголовки) из `third_party/boost_1_60_0` (распакован из boost.zip внутри проекта). Переменные среды и Setup.bat не используются, fallback KENSHILIB_DIR удалён.
- Горячая клавиша заменена файлом-флагом `PackSeller.cmd` рядом с DLL (слова `go | dump | reload`). Причина: проверенного ввода с клавиатуры в api-notes нет (процесс правила 1: не выдумывать API). Плагин опрашивает файл из тика раз в `cmd_poll_ms` и удаляет его. Для релиза будет заменено UI-кнопкой (этап 6).
- Состояния: Idle -> Going -> Returning -> Idle. Состояние Selling появится на этапах 4/7; смена состояния только через функцию `transition()` в `MoveFsm.cpp`, состояние хранится в единственном объекте `Order` (создаётся при первом `go`, без глобальных конструкторов KenshiLib).
- Идентификатор животного: `hand` (не указатель), разрешается каждое обновление через `hand::getCharacter()` + проверка `getHandle() == сохранённый` + dead/destroyed/unconscious/kidnapped/carried. Без разрешения -> Idle без возврата.
- Выбор животного: первое годное из `selectedCharacters`, иначе первое животное в `getAllPlayerCharacters()`.
- Тестовая точка: старт + `test_distance` по первому из +X, -X, +Z, -Z, где `pathExists` истинно; если ни одно направление не прошло, всё равно идём на +X (результат ловит pathFailed/stuck/таймаут). Это осознанная мягкость прототипа: надёжность `pathExists` для животных не проверена. Цель берёт y старта.
- Обновление автомата: раз в `update_interval_ms` реального времени (200 мс), не на паузе. Таймаут: накопленный аргумент `time` хука (единицы не подтверждены) + жёсткий предел 5x по реальному времени. Отклонение от скила (игровое время): единицы `time` неизвестны, пока логируем оба.
- Ошибочные выходы: PATH_FAILED (3 подряд после льготных 10 обновлений), STUCK (>= `stuck_seconds`), ORDER_ENDED_FAR (первого приказа нет 3 раза подряд, далеко), OVERRIDDEN (первый приказ другого типа: Idle без возврата и без сообщения), TIMEOUT_GAME/TIMEOUT_REAL, ANIMAL_* (Idle), WORLD_LOADING (сброс в Idle при загрузке/сбросе мира), BUSY (повторный `go`). Из Going ошибка -> Returning, из Returning -> Idle с сообщением.
- Лог: `DebugLog` с префиксом `[PackSeller]`; подробные строки `[dbg]` включаются `debug_log=1` (по умолчанию включено на этапе тестов). Сообщения игроку через `showPlayerAMessage` (английские, `show_messages`).
- Не сделано в рамках этапа: отмена приказа (не нужна), сохранение состояния (этап 8), продажа.

## Этап 3, исправление после игрового теста M3-11 (перехват приказа игроком)
- Дефект: игрок отдал животному свой move-приказ мышью; ключ задачи остался MOVE_CUS_ORDERED (29), поэтому OVERRIDDEN (проверка по ключу) не сработал, а после окончания приказа игрока сработал ORDER_ENDED_FAR и животное вернули на старт против воли игрока.
- Исправление: перехват определяется по цели задачи. Если первая задача - move и её `getLocation()` отличается от `o.dest` больше чем на `arrival_radius * 2` два обновления подряд (после льготных 10), то Idle с reason=OVERRIDDEN, без возврата и без сообщения (в Going и Returning). Дополнительно запоминается момент смены `getLocation()` задачи; если задача исчезла далеко и смена была не более 30 игровых секунд назад, вместо ORDER_ENDED_FAR выдаётся OVERRIDDEN. Допуск и окно - константы в MoveFsm.cpp (`kForeignTargetFactor`, `kRetargetWindow`), в конфиг не вынесены.
- Допущение по ложным срабатываниям: сравнивается `task loc`, а не `mvDest`. В логах run3/run4 и в эталонном цикле run5 `loc` задачи точно равен запрошенному dest во всех строках status (Going и Returning), без привязки к точкам маршрута; `mvDest` же при перехвате и в начале пути может быть другим (маршрутная точка), поэтому его не используем. В grace-период (10 обновлений) проверка отключена, так что старая задача в первые тики не даёт срабатывания. Не проверено в игре.

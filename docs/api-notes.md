### Автомат
`Idle -> Going -> Selling -> Returning -> Idle`. Единственный объект `Order`, состояние меняет только `transition()`. Обновление раз в `update_interval_ms`, не на паузе, под SEH (исключение = Idle, `reason=EXCEPTION`).
- Старт (`OrderStart(animalHand, traderHand)`; из окна кнопкой «Продать» при `order_enabled=1`, либо `order <index|hand>` в `PackSeller.cmd`): проверки WORLD, BUSY (в т.ч. идёт ли тест `go`), животное (hand разрешается, животное, годно, с игроком), торговец (hand разрешается, не животное, годен). Запоминаются: точка старта = позиция животного, hand животного и торговца, цель = позиция торговца. Сообщение игроку на каждый исход.
- Going: приказ `playerMoveOrderDefault(NULL, NULL, позиция торговца)`. Животное не входит в здания (раздел 2), поэтому «прибытие» широкое: дистанция XZ до торговца <= `trade_range` (150 единиц, подобрано по логам этапа 3: приказ на длинной дистанции заканчивался за ~25 единиц до цели, скорость 15-75 единиц/с; единица ~0.1 м НЕ подтверждена, на метры не опираемся) -> `IN_RANGE` -> Selling. Расширенные исходы: приказ закончился / `pathFailed` / `stuck` на дистанции <= `trade_range * 1.5` -> `ORDER_ENDED_NEAR` / `PATH_FAILED_NEAR` / `STUCK_NEAR` -> Selling.
- Selling: на следующем обновлении `SellRunFor(false, &animal, &trader, &outcome, order_max_items, notify=false)` (правила этапа 4 без изменений; реальная продажа только при `sell_dry_run=0`, иначе расчёт). Исходы: `SOLD` / `SOLD_PARTIAL_ABORTED` / `SOLD_DRY` / `NOTHING_SOLD` / `NOTHING_TO_SELL` / `SELL_ABORTED` / `SELL_NO_PLAN`; во всех случаях дальше Returning (нечего продавать = возврат с сообщением).
- Returning: приказ на точку старта; назад = дистанция до старта <= `arrival_radius` (`ARRIVED_BACK`) либо приказ закончился / `pathFailed` / `stuck` ближе `return_range` (60, ключ добавлен сверх задания: старт - произвольная точка на улице, допуск 150 слишком грубый). Затем Idle.
- Остановка далеко от цели (`ORDER_ENDED_FAR`, `STUCK`): приказ отправляется заново до `retry_orders` (2) раз за фазу (в Going цель берётся из текущей позиции торговца), затем ошибочный выход. `PATH_FAILED` далеко: сразу ошибочный выход (повтор бессмыслен).
- Таймаут одной фазы: `order_timeout_seconds` (300) накопленного аргумента `time` хука (идёт по реальному времени при скорости 1, не идёт на паузе, этап 3) ИЛИ 5x этого значения активного (не на паузе) реального времени.

### Ошибочные выходы (код в логе `state A -> B, reason=CODE`, сообщение игроку RU/EN из `Lang.cpp`)
| Код | Где | Куда | Сообщение |
|---|---|---|---|
| `TRADER_UNRESOLVED`, `TRADER_HANDLE_MISMATCH`, `TRADER_DEAD`, `TRADER_UNCONSCIOUS`, `TRADER_UNAVAILABLE` (похищен/несут), `TRADER_NOT_LOADED` (hand разрешается, но 3 проверки подряд нет в `getCharacterUpdateList()`) | Going; в Selling торговца проверяет `SellRunFor` («requested trader ... gone», код `SELL_NO_PLAN`) | Returning | торговец недоступен |
| `PATH_FAILED`, `STUCK`, `ORDER_ENDED_FAR` (после `retry_orders`) | Going | Returning | путь заблокирован |
| то же | Returning | Idle (животное остаётся) | не удалось вернуться |
| `TIMEOUT_GAME`, `TIMEOUT_REAL` | Going / Returning | Returning / Idle | время вышло |
| `ANIMAL_UNRESOLVED`, `ANIMAL_HANDLE_MISMATCH`, `ANIMAL_DEAD`, `ANIMAL_UNCONSCIOUS`, `ANIMAL_UNAVAILABLE` (destroyed входит в DEAD) | любое | Idle без возврата | животное потеряно |
| `OVERRIDDEN` (чужая move-задача: местоположение отличается от эталонного 2 проверки подряд; первая задача не move; задача исчезла вдали вскоре после смены `getLocation`) | Going / Returning | Idle без возврата | приказ отменён игроком |

Дальше сдвиг эталона больше `2 * arrival_radius` два раза подряд = перехват.

### Подход к торговцу в здании (добавлено по игровым тестам, 2026-10-25)
- Факты логов stage7 run3-5: `pathExists(позиция торговца)=1` даже для торговца внутри здания (предпроверка НЕ надёжна); приказ в позицию Купца (магазин): `PATH_FAILED`, `travelled=0`; Стройторговец (здание, ~1600 ед.): животное прошло ~1200 ед., остановилось в ~577 ед., `PATH_FAILED`; Трактирщик (бар) работал за счёт `IN_RANGE` при 144-148 ед.
- Признак «в здании»: `!Character::isInsideBuilding.isNull()` (поле `hand`, уже используется в `TraderList.cpp`). API двери (`getDoorPosOutside`) и проверки «точка внутри здания» (AABB здания) не использованы: ни то, ни другое не подтверждено; `insideBuilding()` в `Building.h` относится к `PreviewBuilding`, не к `Building`.
- Алгоритм: если торговец в здании и дальше `trade_range` от животного, приказ идёт не в позицию торговца, а в точку кольца радиуса `approach_radius` (0 = `trade_range*0.9`) вокруг него: `approach_candidates` (12) точек, оставляются те, для которых `pathExists` истинно, порядок по расстоянию до животного. Нет ни одной: `NO_APPROACH`, приказ не стартует (сообщение). При `PATH_FAILED` / `STUCK` / `ORDER_ENDED_FAR` далеко: следующая точка (не ближе `0.8*радиус` к уже неудачным, иначе просто следующая), до `retry_orders` (по умолчанию теперь 4) попыток; точки кончились: `NO_APPROACH` (Going -> Returning). Вход в Selling как прежде: `IN_RANGE` (дистанция до ТОРГОВЦА <= `trade_range`, точка кольца 135 < 150) либо остановка ближе `trade_range*1.5`. `OVERRIDDEN` сравнивает с выбранной точкой подхода (`o.p.dest`).
- В лог: `approach: candidate #i (x, z) dAnimal= pathExists=`, `selected candidate k of n ... (причина)`, `retry n/N: reason=..., changing the approach point`. Кандидаты не сохраняются (при загрузке пересобираются).
- Риск: точки кольца могут оказаться внутри того же здания или других зданий; `pathExists` их не отсеивает (см. выше), спасает смена точки. Не проверено в игре.

### Загрузка
Хук H4 только разбирает запись (версия, диапазоны, конечные числа) и вызывает `OrderSetPending`; восстанавливает приказ `OrderTick`, когда мир не грузится: каждые 0.5 с пробует разрешить hand животного (`fromString` + `getCharacter` + совпадение полей hand + животное игрока + годно + есть в списке обновления) и, для Going, торговца. Не разрешились за 60 с реального времени: приказ сбрасывается в Idle без возврата, сообщение «Приказ животному потерян при загрузке» (hand до загрузки мог называть старый объект, DC; поэтому ожидание, а не мгновенный отказ). Исполнение: Going/Returning приказ переотдаётся (`transition(..., "LOADED_FROM_SAVE")`), для торговца в здании кольцо подхода пересобирается и выбирается точка, совпавшая с сохранённой целью; таймер фазы продолжается (`phase`), повторы восстанавливаются.
- Selling откатывается в Returning. Двойной продажи быть не может: продажа выполняется целиком в одном обновлении (деньги, предметы, переход Selling -> Returning в одном кадре, `Sell.cpp`), поэтому в сейве состояние Selling означает «продажа ещё не выполнена», а Returning/Idle «продажа уже в сохранённом инвентаре и кошельке»; откат в Returning никогда не продаёт повторно (максимум - не продаёт совсем; это принято лидом).
- Нет записи (старый сейв, сейв без приказа, мод был выключен): `LOAD ... no record`, Idle, поведение как раньше.

### 1. Как принято добавлять настройки мода
Статус: подтверждено кодом (4 плагина) и описаниями.
- (а) Вкладка в окне Options - самый распространённый способ. Хук `OptionsWindow::create`, затем `tabs->insertItemAt(...)` и панель строк игры. KEP: `kep-core/src/config_manager.cpp` (`ConfigManager::create`: вкладка "KEP" на позиции 5, `gui->createDatapanel("kep_options", tab, true)`, `changeCategory`, `setItemData(tab, panel)`). MCM (LEOPARD `ModConfigMenu/ModConfigMenu.cpp:2074-2076`, вкладка "MCM" ПЕРЕД последней ванильной "МОДЫ"; `createDatapanel` на 1633; хуки 2676-2696). Комментарий MCM (строки 24-30): RE_Kenshi и Steel Mods вешают кнопки на ПОСЛЕДНЮЮ вкладку окна (`getItemAt(getItemCount() - 1)`), поэтому свои вкладки вставляют перед последней.
- (б) Кнопка в главном меню: ни один из прочитанных плагинов так не делает. Макет `Kenshi_MainMenu.layout` принадлежит игре (кнопки ContinueButton, NewGameButton, LoadGameButton, ImportGameButton, OptionsButton, CreditsButton, ExitButton, размеры и позиции заданы долями экрана, свободного места нет). Esc-меню в игре - `Kenshi_MainMenuPopupPanel.layout` (NewGame, SaveGame, LoadGame, Options, ExitGame, Resume). Обе кнопки OPTIONS открывают окно настроек (`TitleScreen::showOptions(Widget*)`, `OptionsWindow::getSingleton()`). Вывод: общепринятый путь - "главное меню (или Esc) -> OPTIONS -> вкладка/кнопка мода".
- (в) RE_Kenshi сам: кнопка "RE_Kenshi Settings" на ПОСЛЕДНЕЙ вкладке (MODS) окна настроек, открывающая собственное окно `Kenshi_WindowCX` с `Kenshi_TabControl` и чекбоксами `Kenshi_TickBoxSkin` (RE_Kenshi `dllmain.cpp`: `InjectSettings`, `InitGUI`, `CreateStandardTickButton`; инициализация из хука `ForgottenGUI::changeFontSize`, внедрение кнопки каждый кадр из `Gui::eventFrameStart`, вкладка находится по имени виджета "OptionsTab"; Esc окном не обрабатывается). Путь для пользователя - OPTIONS -> MODS -> RE_KENSHI SETTINGS из главного меню и из Esc-меню (страница RE_Kenshi на Nexus, mods/847, по выдержке поиска). API RE_Kenshi для плагинов "зарегистрировать вкладку/элемент" НЕ найдено: ни в вики-страницах (Home, FAQ, Features, Finding file paths, heightmap, hard coded file paths, sound banks), ни в `Plugins.cpp` (только загрузка DLL по `RE_Kenshi.json` и вызов экспорта `startPlugin`). Каждый плагин встраивается сам.
- Вариант "кнопка рядом со строкой своего мода во вкладке MODS и своё окно" (Au2942: MoreImmersiveBars `src/MoreImmersiveBars.cpp:477-550`, SquadAutonomy `src/SquadAutonomy.cpp:329-408`): в хуке `OptionsWindow::create` среди вкладок ищут панель с `panelName == "Active_Mods"` (подпись вкладки зависит от языка, поэтому по имени панели), перебирают строки `getLineByNum(0, i)`, у `line->keyValue` (вид "<что-то> - <имя мода>") берут часть после `-` и сравнивают с именем мода; рядом с правым текстом строки (`line->w2`, "version x") создают `Kenshi_Button1`, по нему открывают собственное окно `createDatapanel(top,left,w,h,true,"Window",true)` с `setCaption`, `setCloseCallback`, `show(true)`, `LayerManager::upLayerItem`. Хрупко: зависит от точного имени мода и устройства строки.
- Вкладка "все моды": ModConfigMenu (LEOPARD, `LEOPARD/ModConfigMenu/README.txt`, `sdk/MCM_API_en.md`) - необязательная зависимость: плагин экспортирует `extern "C" __declspec(dllexport) void MCM_Describe(MCM_Api*)` и описывает строки (toggle, integer, number, choice, text, hotkey, colour). Значения в ini плагина (секции обязательны, UTF-8 без BOM), MCM пишет `WritePrivateProfileString` и зовёт функцию `apply`. Наш `PackSeller.cfg` (ключ=значение без секций) для этого не подходит без изменения формата. Годится как позднее необязательное дополнение, не как основной способ.
- (г) Emkej's Mod Core / Mod Hub: вкладка "Mod Hub" в Options (Nexus mods/1885, 1900, 1953, 1871 по результатам поиска); жёсткая сторонняя зависимость (Mod Core должен стоять выше интегрирующихся модов). SDK (заголовки) не найден (у MCM есть мост `shared/McmModHubBridge.h` с сигнатурами `EMC_*Callback`, но это чужой интерфейс). Нежелательно.
- Hidden Faction Relations: утверждение о вкладке в Options исходником не подтверждено. Известно только из README MCM, что форк описан через MCM и имеет свой вызов окна `MCM_OpenPage`. Не проверялось.
- Совместимость: хук `OptionsWindow::create` независимо используют MCM, KEP, MoreImmersiveBars, SquadAutonomy (KenshiLib рассчитана на несколько плагинов на одной функции, раздел 9). На машине пользователя в логе (`logs/RE_Kenshi_log_town02_run4.txt`) загружены KEP 0.17.3 и KenshiRotate (хукает `OptionsWindow::_NV_update`). KenshiRotate внедряет виджеты в вкладку MODS по именам (`src/Settings.cpp:301-430`: ищет вкладку по подписи "MODS", затем по суффиксу имени, затем по индексу 5). Значит: вставлять свою вкладку перед последней, вкладку MODS и ванильные вкладки не трогать, имена своих виджетов уникальные (`PackSeller_*`).

### 3. Главное меню до загрузки сейва
- Наш хук тика H1 `GameWorld::_NV_mainLoop_GPUSensitiveStuff` в главном меню НЕ вызывается. Доказательство - собственный лог `logs/RE_Kenshi_log_town02_run4.txt`: `8.266 RE_Kenshi: Main menu loaded.`, `21.149 RE_Kenshi: In-game.`, `21.648 persist: LOAD #1`, первая строка нашего тика `22.348 first tick`; за ~13 с меню тик не вызывался. Хуки при этом стоят заранее (`6.673 Hooked GameWorld::_NV_mainLoop...` до `8.266`), т.е. хук `OptionsWindow::create` установится до меню. `ou` в меню использовать нельзя (может не существовать).
- Что в меню работает: `TitleScreen::_NV_update` (хук KenshiCoop `src/plugin/Plugin.cpp:1705`, `GetRealAddress(&TitleScreen::_NV_update)` на 2300; панель на экране заголовка рисуется под SEH), `MyGUI::Gui::eventFrameStart` (RE_Kenshi `GUIUpdate`; `mygui/MyGUI_Gui.h:150`), `ForgottenGUI::changeFontSize` (RE_Kenshi, MoreImmersiveBars), `OptionsWindow::_NV_update` (KenshiRotate, MCM). RE_Kenshi `InitGUI` ждёт виджета "VersionText" главного меню.
- Когда вызывается `OptionsWindow::create` и пересоздаётся ли окно: НЕ УСТАНОВЛЕНО `[TO VERIFY в игре]`. Данные расходятся: `MCM_API_en.md` ("Once, when the game first creates the Options window"), но README MCM (версия 2) описывает пересоздание интерфейса модом ReturnToMainMenu ("строит вкладку заново при следующем открытии окна"), а KenshiRotate (`src/KenshiRotate.cpp:651-660`) комментирует "Options tab widgets are destroyed when the menu closes, so re-inject every frame" и внедряется из `_NV_update`. Поле `OptionsWindow::created` (0x110) намекает на ленивое создание. Для кода: хук `create` идемпотентный, указатели на вкладку, панель и виджеты между вызовами не хранить, перед добавлением проверять, нет ли нашей вкладки (по подписи и уникальному имени), пересобирать при каждом вызове; добавить диагностику (счётчик и время вызовов `create`, число вкладок, есть ли наша вкладка при первых вызовах `_NV_update`).
- Esc-меню в игре: та же кнопка OPTIONS (`Kenshi_MainMenuPopupPanel.layout`) и тот же синглтон; RE_Kenshi указывает один путь для главного меню и Esc (Nexus mods/847). Вкладка из `create` должна быть видна в обоих `[TO VERIFY в игре]`. Закрытие (кнопка CLOSE, Esc) ведёт игра; наш код не закрывает окно и не опрашивает клавиши; модальность не нужна.
- Поток: события клика идут в потоке интерфейса игры. Обработчики ограничены записью флагов и пересборкой собственной страницы; игровые объекты (`ou`, персонажи) не трогаем. Тело хука и обработчики - под SEH (`Seh.h`), как у MCM и KenshiCoop.

### 4. Хранение настроек
- Сейчас: `PackSeller.cfg` (`ключ=значение`, `#`/`;`) рядом с DLL (`Config.cpp` `GetModuleDir`; в логе `...\Kenshi\mods\PackSeller\PackSeller.cfg`), читается целиком `LoadConfig()`; `ui_language=auto|en|ru`, `debug_log`; язык решается один раз в `LangInit()` (`g_ru`), лог проверяет `GetConfig().debugLog` на каждой записи (`Log.cpp:52`), т.е. `debug_log` можно менять на лету.
- Образцы: MoreImmersiveBars переписывает свой `.cfg` целиком при закрытии окна и в хуке `saveOptions` (без временного файла, без обработки ошибок записи); MCM `WritePrivateProfileString` меняет одну строку (комментарии целы); LEOPARD `shared/IniDefaults.h` (комментарий от 11.10.2026): в раздачу идёт `<Мод>.defaults.ini`, `<Мод>.ini` принадлежит игроку, чтобы обновление его не затирало.
- Рекомендация (проектное решение): `PackSeller.cfg` остаётся раздаваемым файлом с комментариями и программно НЕ переписывается; изменённые из игры настройки (`debug_log`, `ui_language`) пишутся в отдельный `PackSeller.user.cfg` рядом с DLL, читаемый ПОСЛЕ основного и переопределяющий его, в раздачу не включается. Формат тот же `ключ=значение`, парсер `LoadConfig()` переиспользуется (второй проход).
- Безопасная запись (Win32, C++03): полный текст в `PackSeller.user.cfg.tmp` (`std::ofstream`, проверка `good()` после закрытия), затем `MoveFileExA(tmp, dst, MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` (MS Learn, `MoveFileExA`: заменяет существующий файл, ждёт записи на диск; атомарность документация явно не обещает). Ошибка (папка только для чтения, файл занят): прежний файл не трогать, `GetLastError()` в лог, значение применить в памяти на сессию, в окне настроек одна подсказка в подписи строки (`showPlayerAMessage` в меню недоступен, `ou` может быть NULL). Запись по изменению и при закрытии, не в тике. Права на папку Workshop (`steamapps\workshop\content\233860\<id>`) и поведение Steam при обновлении (удаляет ли лишние файлы) `[TO VERIFY]`; запасной путь, только если проверка покажет проблему: `%LOCALAPPDATA%\PackSeller\PackSeller.user.cfg` (читать: папка мода, затем этот каталог).
- Применение без перезапуска: `debug_log` - присвоить `GetConfig().debugLog`; язык - новая функция `LangSetRussian(bool)` вместо повторного `LangInit()` (тот перечитывает `settings.cfg`, `Lang.cpp:226-243`) и `uiLanguage = "ru"/"en"`; затем `clearPage` + строки заново и `tab->setCaption(...)`; открытое окно торговцев перерисуется при следующем открытии. Полный `LoadConfig()` из UI не нужен.
- Язык и шрифт: кириллица есть только при `language=ru_RU` (раздел 9). Выбор "Русский" при другом языке игры даст квадраты: в этом случае строку русского блокировать/скрывать или предупреждать, подписи вкладки на английском. Добавить около 8 строк на язык в `kStrings`.

### 5. Рекомендация
**Собственная вкладка "PackSeller" в окне Options, построенная строками игры (`DatapanelGUI`) в хуке `OptionsWindow::create`, вставка перед последней (ванильной MODS) вкладкой.** Доступна из главного меню (OPTIONS) и из Esc-меню. Основания: (1) тот же приём у KEP, MCM, MoreImmersiveBars, SquadAutonomy, несколько плагинов на одном хуке допустимо; (2) жизненный цикл, закрытие, Esc, шрифты, подсказки ведёт игра; (3) не нужны тик в меню, `ou`, свои MyGUI-окна, модальность; (4) нет внешних зависимостей; (5) чекбокс "Режим отладки" - готовая строка `setLineCheckbox(label, &bool, cat)`.
- Хуки: один новый (H5) `OptionsWindow::create` (оригинал вызывается всегда первым, затем наш код под SEH, идемпотентно). Опционально H6 `OptionsWindow::saveOptions` (сброс файла при закрытии).

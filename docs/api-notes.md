### Автомат
`Idle -> Going -> Selling -> Returning -> Idle`. Единственный объект `Order`, состояние меняет только `transition()`. Обновление раз в `update_interval_ms`, не на паузе, под SEH (исключение = Idle, `reason=EXCEPTION`).
- Старт (`OrderStart(animalHand, traderHand)`; из окна кнопкой «Продать» при `order_enabled=1`, либо `order <index|hand>` в `PackSeller.cmd`): проверки WORLD, BUSY (в т.ч. идёт ли тест `go`), животное (hand разрешается, животное, годно, с игроком), торговец (hand разрешается, не животное, годен). Запоминаются: точка старта = позиция животного, hand животного и торговца, цель = позиция торговца. Сообщение игроку на каждый исход.
- Going: приказ `playerMoveOrderDefault(NULL, NULL, позиция торговца)`. Животное не входит в здания (раздел 2), поэтому «прибытие» широкое: дистанция XZ до торговца <= `trade_range` (150 единиц, подобрано по логам этапа 3: приказ на длинной дистанции заканчивался за ~25 единиц до цели, скорость 15-75 единиц/с; единица ~0.1 м НЕ подтверждена, на метры не опираемся) -> `IN_RANGE` -> Selling. Расширенные исходы: приказ закончился / `pathFailed` / `stuck` на дистанции <= `trade_range * 1.5` -> `ORDER_ENDED_NEAR` / `PATH_FAILED_NEAR` / `STUCK_NEAR` -> Selling.
- Selling: на следующем обновлении `SellRunFor(false, &animal, &trader, &outcome, order_max_items, notify=false)` (правила этапа 4 без изменений; реальная продажа только при `sell_dry_run=0`, иначе расчёт). Исходы: `SOLD` / `SOLD_PARTIAL_ABORTED` / `SOLD_DRY` / `NOTHING_SOLD` / `NOTHING_TO_SELL` / `SELL_ABORTED` / `SELL_NO_PLAN`; во всех случаях дальше Returning (нечего продавать = возврат с сообщением).
- Returning: приказ на точку старта; назад = дистанция до старта <= `arrival_radius` (`ARRIVED_BACK`) либо приказ закончился / `pathFailed` / `stuck` ближе `return_range` (60, ключ добавлен сверх задания: старт - произвольная точка на улице, допуск 150 слишком грубый). Затем Idle.
- Остановка далеко от цели (`ORDER_ENDED_FAR`, `STUCK`): приказ отправляется заново до `retry_orders` (2) раз за фазу (в Going цель берётся из текущей позиции торговца), затем ошибочный выход. `PATH_FAILED` далеко: сразу ошибочный выход (повтор бессмыслен).
- Таймаут одной фазы: `order_timeout_seconds` (300) накопленного аргумента `time` хука (идёт по реальному времени при скорости 1, не идёт на паузе, этап 3) ИЛИ 5x этого значения активного (не на паузе) реального времени.

### Ошибочные выходы (код в логе `state A -> B, reason=CODE`, сообщение игроку RU/EN из `Lang.cpp`)
| Код | Где | Куда | Сообщение |
|---|---|---|---|
| `TRADER_UNRESOLVED`, `TRADER_HANDLE_MISMATCH`, `TRADER_DEAD`, `TRADER_UNCONSCIOUS`, `TRADER_UNAVAILABLE` (похищен/несут), `TRADER_NOT_LOADED` (hand разрешается, но 3 проверки подряд нет в `getCharacterUpdateList()`) | Going; в Selling торговца проверяет `SellRunFor` («requested trader ... gone», код `SELL_NO_PLAN`) | Returning | торговец недоступен |
| `PATH_FAILED`, `STUCK`, `ORDER_ENDED_FAR` (после `retry_orders`) | Going | Returning | путь заблокирован |
| то же | Returning | Idle (животное остаётся) | не удалось вернуться |
| `TIMEOUT_GAME`, `TIMEOUT_REAL` | Going / Returning | Returning / Idle | время вышло |
| `ANIMAL_UNRESOLVED`, `ANIMAL_HANDLE_MISMATCH`, `ANIMAL_DEAD`, `ANIMAL_UNCONSCIOUS`, `ANIMAL_UNAVAILABLE` (destroyed входит в DEAD) | любое | Idle без возврата | животное потеряно |
| `OVERRIDDEN` (чужая move-задача: местоположение отличается от эталонного 2 проверки подряд; первая задача не move; задача исчезла вдали вскоре после смены `getLocation`) | Going / Returning | Idle без возврата | приказ отменён игроком |

Дальше сдвиг эталона больше `2 * arrival_radius` два раза подряд = перехват.

### Подход к торговцу в здании (добавлено по игровым тестам, 2026-10-25)
- Факты логов stage7 run3-5: `pathExists(позиция торговца)=1` даже для торговца внутри здания (предпроверка НЕ надёжна); приказ в позицию Купца (магазин): `PATH_FAILED`, `travelled=0`; Стройторговец (здание, ~1600 ед.): животное прошло ~1200 ед., остановилось в ~577 ед., `PATH_FAILED`; Трактирщик (бар) работал за счёт `IN_RANGE` при 144-148 ед.
- Признак «в здании»: `!Character::isInsideBuilding.isNull()` (поле `hand`, уже используется в `TraderList.cpp`). API двери (`getDoorPosOutside`) и проверки «точка внутри здания» (AABB здания) не использованы: ни то, ни другое не подтверждено; `insideBuilding()` в `Building.h` относится к `PreviewBuilding`, не к `Building`.
- Алгоритм: если торговец в здании и дальше `trade_range` от животного, приказ идёт не в позицию торговца, а в точку кольца радиуса `approach_radius` (0 = `trade_range*0.9`) вокруг него: `approach_candidates` (12) точек, оставляются те, для которых `pathExists` истинно, порядок по расстоянию до животного. Нет ни одной: `NO_APPROACH`, приказ не стартует (сообщение). При `PATH_FAILED` / `STUCK` / `ORDER_ENDED_FAR` далеко: следующая точка (не ближе `0.8*радиус` к уже неудачным, иначе просто следующая), до `retry_orders` (по умолчанию теперь 4) попыток; точки кончились: `NO_APPROACH` (Going -> Returning). Вход в Selling как прежде: `IN_RANGE` (дистанция до ТОРГОВЦА <= `trade_range`, точка кольца 135 < 150) либо остановка ближе `trade_range*1.5`. `OVERRIDDEN` сравнивает с выбранной точкой подхода (`o.p.dest`).
- В лог: `approach: candidate #i (x, z) dAnimal= pathExists=`, `selected candidate k of n ... (причина)`, `retry n/N: reason=..., changing the approach point`. Кандидаты не сохраняются (при загрузке пересобираются).
- Риск: точки кольца могут оказаться внутри того же здания или других зданий; `pathExists` их не отсеивает (см. выше), спасает смена точки. Не проверено в игре.

### Загрузка
Хук H4 только разбирает запись (версия, диапазоны, конечные числа) и вызывает `OrderSetPending`; восстанавливает приказ `OrderTick`, когда мир не грузится: каждые 0.5 с пробует разрешить hand животного (`fromString` + `getCharacter` + совпадение полей hand + животное игрока + годно + есть в списке обновления) и, для Going, торговца. Не разрешились за 60 с реального времени: приказ сбрасывается в Idle без возврата, сообщение «Приказ животному потерян при загрузке» (hand до загрузки мог называть старый объект, DC; поэтому ожидание, а не мгновенный отказ). Исполнение: Going/Returning приказ переотдаётся (`transition(..., "LOADED_FROM_SAVE")`), для торговца в здании кольцо подхода пересобирается и выбирается точка, совпавшая с сохранённой целью; таймер фазы продолжается (`phase`), повторы восстанавливаются.
- Selling откатывается в Returning. Двойной продажи быть не может: продажа выполняется целиком в одном обновлении (деньги, предметы, переход Selling -> Returning в одном кадре, `Sell.cpp`), поэтому в сейве состояние Selling означает «продажа ещё не выполнена», а Returning/Idle «продажа уже в сохранённом инвентаре и кошельке»; откат в Returning никогда не продаёт повторно (максимум - не продаёт совсем; это принято лидом).
- Нет записи (старый сейв, сейв без приказа, мод был выключен): `LOAD ... no record`, Idle, поведение как раньше.

### Сейв с записью при ВЫКЛЮЧЕННОМ моде [TO VERIFY в игре]
Что известно: автор kenshi-achievements заявляет (README, CHANGELOG), что сейвы с его записью типа 4242 грузятся без мода нормально, а сохранение без мода запись выбрасывает; плагин выпущен в Steam Workshop. Заголовки и lib не дают способа проверить обработку неизвестного `itemType` (тело загрузчика недоступно). Принятая схема совпадает с рабочей чужой (свой тип в пределах 1100-55000, запись только при активном приказе, т.е. редко). Риск: поведение при неизвестном типе не проверено нами; смягчение: запись создаётся только во время приказа (окно в десятки секунд), ключ `save_enabled=0` отключает хуки. Проверка: V8-6 в test-plan.md (сейв во время приказа, отключить мод, загрузить, сохранить, включить, загрузить). Запасной вариант на случай краша: записывать данные в стандартную запись известного типа в служебное поле (не реализован).

### Не подтверждено в игре
Хуки H3/H4 срабатывают при ручном сохранении, автосохранении и быстром сохранении; `createNewData` в `saveGameState` не возвращает NULL; запись попадает в `ou->savedata.gamedataSID` при загрузке; hand животного и торговца разрешаются после загрузки теми же строками; переотданный приказ работает; сейв с записью грузится без мода.

## Актуализация к релизу 0.1.0 (2026-10-27, ps-plugin-dev, по ревью QA)
- Хуки: четыре, все через `KenshiLib::AddHook`, оригиналы вызываются: H1 тик, H2 `InventoryGUI::_CONSTRUCTOR`, H3 `FactionManager::saveGameState`, H4 `GameWorld::loadAllPlatoons`. H2, H3, H4 установились и сработали в игре (сообщение лида по тестам этапов 6-8); H5 не используется.
- Подтверждено в игре (логи этапов 3-8, решения лида): приказ `playerMoveOrderDefault` невыделенному животному, прибытие по своей дистанции (`isDestinationReached` не используется), перехват приказа игроком по эталону `getLocation()` задачи, таймаут, пауза, загрузка мира, программная продажа (части стопок, деньги и предметы совпали с расчётом), подход к торговцу в здании точкой на кольце (`pathExists` для точек кольца не вызывается: он давал 1 даже для точек внутри зданий и ничего не фильтровал (вылеты run 6-7 в итоге объяснены ODR, а не им)), запись и чтение GameData типа 20717.
- Корневая причина вылетов разработки: ODR (два разных `struct Order` в одном `namespace PS` склеились линковщиком). Правило: типы единицы трансляции в анонимном namespace (сделано для всех .cpp), имена в `PS` уникальны.
- SEH-обёртки ловят только аппаратные ошибки (`PsSehFilterCode` в `Seh.h`: нарушение доступа, ошибка страницы, выход за границы, нарушение выравнивания, недопустимая/привилегированная инструкция, деление на ноль, переполнение целого, ошибки FPU). C++ исключения, точки останова и прочее проходят дальше (`EXCEPTION_CONTINUE_SEARCH`). Переполнение стека не ловится намеренно.
- Враждебность торговца (`TraderIsHostile`, `hostile_policy`): враг игрока по фракции торговца или по фракции его города (`Faction::relations->isEnemy`), правило то же, что пометка в окне. `block` (по умолчанию): `OrderStart` отказывает; `warn`: сообщение и приказ идёт; `allow`: как раньше. Не проверено в игре (нет враждебного города в загруженной зоне).
- Отладочный интерфейс (`PackSeller.cmd`): читается только при `debug_commands=1`; кнопка окна от ключа не зависит.
- По-прежнему НЕ подтверждено в игре: загрузка сейва с нашей записью при ВЫКЛЮЧЕННОМ моде (риск этапа 8, V8-6), кочевые торговцы, враждебный город (policy), типы поселений кроме городов, `ui_modal=1`, совместимость с Organize the Inventory, Kenshi 1.0.68, сохранение именно в состоянии Selling, смерть и потеря сознания животного/торговца в пути (E9-*), работа хука сохранения вне главного потока.

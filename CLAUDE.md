# PackSeller — автопродажа вьючника (мод Kenshi, RE_Kenshi / KenshiLib)

Отдельный мод, не связан с «Призвать наёмников». Полный дизайн: `docs/design.md` (источник истины по требованиям).
Язык общения с пользователем и документации: русский. Идентификаторы и комментарии в коде: английский.

## Что делаем

C++ плагин для RE_Kenshi. В инвентаре вьючного животного кнопка «Торговцы» открывает модальное окно со списком городских торговцев (имя, город, расстояние, деньги, кнопка «Продать»). По клику животное идёт к торговцу, при входе в зону взаимодействия происходит программная продажа, затем животное возвращается на точку старта.
Версия 0.1 включает: сортировку списка, скрытие неподходящих торговцев, пометку враждебных городов. Всё остальное в `docs/design.md` → «Не входит».

## Жёсткие правила

1. **Не выдумывать API.** Любой класс, функция, поле, смещение, хук сверяются с исходниками KenshiLib, примерами KenshiLib_Examples или кодом существующих плагинов. Непроверенное помечается `[TO VERIFY]` и не попадает в код без проверки. Проверенное записывается в `docs/api-notes.md` с источником (репозиторий, файл, коммит).
2. **Компилятор: Visual C++ 2010 (v100) x64** — требование KenshiLib. Никакого C++11 и новее: без `auto`, лямбд, `nullptr`, range-for, `std::thread`/`std::chrono`. Boost и Ogre/MyGUI берутся из deps.
3. **Хуки только через встроенную систему KenshiLib.** Никаких сторонних библиотек перехвата. Минимум хуков, каждый обосновывается в `docs/api-notes.md`.
4. **Все изменения состояния игры выполняются в главном потоке игры**, внутри хука или колбэка. Никаких собственных потоков, работающих с объектами игры.
5. **Защитное программирование.** Любой указатель на игровой объект проверяется перед использованием: объект мог быть удалён, умереть, выгрузиться вместе с клеткой мира. Хранить указатели между кадрами только через механизм, подтверждённый в api-notes (например, идентификатор или хэндл), иначе перепроверять на каждом тике.
6. **Состояние (приказ) переживает сохранение и загрузку.** Реализуется по образцу WorldStates из KenshiLib_Examples `[TO VERIFY]`. Старые сейвы без нашего мода должны загружаться, сейвы с модом должны загружаться после его отключения без крашей.
7. **Лицензия GPLv3** (KenshiLib). Заголовок лицензии в исходниках, копия лицензии в репозитории.
8. **Установка в папку игры и любые действия за пределами папки проекта только с подтверждения пользователя.** Файлы игры, сейвы и другие моды не изменять.
9. **Не заявлять о работоспособности без проверки.** Сборка и игровые тесты на машине пользователя недоступны без его участия: результат этапа считается принятым, только когда пройдены критерии приёмки из этого файла. Что не проверено в игре, так и пишется в отчёте.
10. Версии игры, RE_Kenshi, KenshiLib и toolchain фиксируются в `README.md`. Целевые версии игры на момент старта: 1.0.65 и 1.0.68 `[TO VERIFY: актуальные]`.

## Команда (агенты в `.claude/agents/`)

| Агент | Зона ответственности |
|---|---|
| `ps-lead` | Планирование, приёмка этапов, ведение `decisions.md`, разрешение конфликтов между ролями |
| `ps-api-researcher` | Этап 2: чтение исходников KenshiLib, заполнение `api-notes.md` |
| `ps-plugin-dev` | Движение животного, продажа, конечный автомат, сохранение, конфиг |
| `ps-ui-dev` | Кнопка в инвентаре, модальное окно MyGUI, локализация |
| `ps-qa` | Тест-план, чек-листы для игры, анализ логов, ревью на крашеопасные места |
| `ps-release` | README, RE_Kenshi.json, упаковка, версии, лицензия |

Лид координирует, остальные работают в своих зонах и не расходятся с `api-notes.md`. Ревью кода выполняет `ps-qa` перед приёмкой каждого этапа.

## Скилы проекта (`.claude/skills/`)

- `kenshilib-api-research` — как исследовать API и оформлять находки.
- `plugin-build` — окружение, сборка, ограничения v100.
- `mygui-ui` — безопасное создание UI, кнопка в инвентаре, модальное окно.
- `trader-sell-logic` — список торговцев, фильтры, программная продажа.
- `pack-animal-fsm` — приказ животному, конечный автомат, возврат, ошибки.
- `packseller-testing` — тест-план, анализ логов, совместимость сейвов.
- `release-packaging` — упаковка и выпуск.

## Процесс и критерии приёмки

Этапы идут по плану из `docs/design.md`. Переход к следующему этапу только после приёмки лидом по критериям ниже. Если этап 3 или 5 оказывается неосуществимым, работа останавливается, лид готовит пересмотр плана для пользователя.

| Этап | Результат | Критерии приёмки |
|---|---|---|
| 1. Окружение | Каркас проекта, Hello World собирается и загружается | Пользователь подтвердил версию игры и toolchain; в логе RE_Kenshi есть строка плагина; версии записаны в README |
| 2. Исследование API | `docs/api-notes.md` | Закрыты все `[TO VERIFY]` из design.md, у каждой записи указан источник; для каждого пункта риска 1–4 и 7 есть вывод «реализуемо / как / альтернатива» |
| 3. Движение | Животное идёт в точку, прибытие фиксируется, возврат на старт | Работает на тестовом животном; обработаны недостижимая цель и таймаут; нет утечки состояния при смерти животного |
| 4. Продажа | Программная продажа выбранному торговцу | Деньги и предметы меняются корректно; торговец не уходит в минус; нескупаемые предметы остаются |
| 5. Список торговцев | Список городских торговцев с городом, расстоянием, деньгами | Кочевые не попадают; фильтр неподходящих; отношение фракции определено; радиус из конфига |
| 6. UI | Кнопка и окно | Кнопка под кнопкой конечностей; окно закрывается без ошибок; сортировка; пометка враждебных; русский текст отображается; нет конфликта с чужими модами окна инвентаря |
| 7. Автомат | Полный цикл + ошибки | Все ошибочные выходы из design.md покрыты и протестированы |
| 8. Сохранения | Приказ переживает save/load | Сохранение в пути и в продаже; загрузка старого сейва; загрузка с отключённым модом |
| 9. Тест и упаковка | Релизный архив | Пройден весь `test-plan.md`; README и RE_Kenshi.json готовы; пользователь установил и проверил |

## Формат отчётов агентов

Короткий отчёт: что сделано, что проверено и как, что НЕ проверено, найденные риски, следующий шаг. Без пересказа шагов.

## Конфиг по умолчанию

Радиус поиска городов, таймаут приказа, отладочный лог. Файл конфига и формат уточняются на этапе 2 `[TO VERIFY]`.
